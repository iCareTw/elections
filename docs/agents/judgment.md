# 判斷力外化（judgment）

把高階模型才擅長的判斷寫成可執行的 rubric。每條附正例與反例。讀者是 Sonnet 等級的模型：**符合判準就照做，不要憑感覺覆寫**。

## 1. 何時該升級模型（haiku→sonnet→opus→問 user）

升級訊號（命中任一即升級）：

- 同一任務同級失敗 2 次，且第二次不是 prompt 問題。
- 任務需要「取捨」而非「執行」：兩個以上合理方案、各有代價、選錯難回頭（schema 設計、資料修正策略、公開介面命名）。
- 跨 3 個以上模組追因果的除錯。

**正例**：voter_guide 的 PDF 解析對某類公報持續誤判，sonnet 修了兩輪、測試仍紅，且每輪的失敗樣本不同 → 升 opus 重新分析根因，而非第三輪修補。
**反例**：批次把 20 個檔案裡的 `台` 改 `臺`，其中一個檔案 grep 沒中 → 這是 pattern 沒寫對，補 pattern 重跑即可，不需升級。

## 2. 何時算真的完成（definition of done）

同時滿足才算完成，缺一項就明說「未完成，缺 X」：

1. 驗收條件在動手前就寫下（不是事後補）。
2. `uv run pytest` 綠，且新行為有對應測試。
3. 受影響的流程實跑過至少一條 happy path（web 功能要真的打開頁面或打 API）。
4. fresh-context verifier 判「通過」且附證據（見 `dispatch.md` 第 5 節）。
5. 有 migration 就同步更新了 `docs/db-schema.md`。

**正例**：新增欄位修復功能——先寫測試、實作、`uv run pytest` 綠、`uv run python -m src.webapp.app` 啟動後實際點過一輪流程、verifier read-back 通過 → 回報完成。
**反例**：「程式碼寫完了、邏輯上應該沒問題、測試等 user 要再跑」→ 這是第 2、3、4 項全缺，只能回報「已實作、尚未驗證」。

## 3. 何時該停下來問 user

問的成本很低，錯的成本很高。命中任一就停：

- 要執行 DB 破壞性操作（CLAUDE.md 絕對規則，無例外）。
- 任務有兩種以上解讀，且做錯要重來（例：「清掉舊資料」是刪 DB 還是刪 `_out/`？）。
- 即將刪除或覆蓋不是自己建立的檔案，且與描述不符。
- 發現 user 的前提可能是錯的（user 說「A 壞了」但證據指向 A 正常、B 壞了）→ 報告發現，不要照原指令硬做。
- 同一任務已失敗 3 次。

**正例**：user 說「把重複的候選人合併」，但 DB 裡「重複」有同名同選區與同名不同選區兩種情況，合併策略不同 → 列出兩種情況與各自筆數，問 user 要哪種。
**反例**：實作時發現要多加一個 import → 這是實作細節，直接做，不要問。

## 4. 方向錯了的訊號（換路，而非重試）

重試只對「隨機失敗」有效。以下訊號代表方向錯了，繼續重試是浪費：

- 每修一處就冒出新的失敗，且失敗點在擴散而非收斂。
- 為了讓方案成立，開始加第 2 個特例／workaround。
- 發現自己在跟框架或函式庫「對抗」（要 monkey-patch、要繞過它的設計）。
- 解釋不了為什麼上一次會失敗，只是「再試一次看看」。

換路的動作：停下 → 用一段話寫下目前假設與反證 → 回到上一個確定正確的狀態（git stash / checkout）→ 產生 2 個替代方案再選。

**正例**：裁切照片的 bbox 對 A 版面對、B 版面錯，修 B 又壞 A，來回三次 → 停下，發現兩種版面需要先分類再各自處理，而非找萬用公式。
**反例**：測試偶爾因 port 被占用而紅 → 這是環境隨機失敗，重跑即可，不是方向問題。

## 5. 品質底線怎麼驗

最低成本的驗法，按序執行，過不了就不出手：

1. **自問一句**：「資深工程師會說這寫複雜了嗎？」會 → 先簡化再交（可跑 `/simplify`）。
2. **diff 逐行對照需求**：每一行改動都能對應到 user 的要求；對不上的行刪掉。
3. **文件類**：內文引用的每個路徑、工具名、指令，實際存在且拼字正確（grep 驗證）。
4. **資料類**：改動前後各跑一次筆數／分布查詢，差異能解釋才算數。

## 6. 誠實條款：這套制度補不了的事

拆解、驗證、多樣本評審能補「執行品質」；以下補不了，遇到就照指示辦：

- **模糊需求**：驗收條件寫不出來的任務，不要開工。先用 2~3 個具體解讀問 user 選（附各解讀的後果）。
- **品味判斷**（UI 好不好看、文案順不順、API 設計優不優雅）：多產幾個候選讓 user 挑，或派 `codex:codex-rescue` 拿外部第二意見；不要單獨硬判。
- **產品方向**（該不該做這個功能）：永遠是 user 的決定。提供資訊，不代決。
- 以上都不適用時，明說「這題超出我能可靠判斷的範圍」比硬給答案好。
